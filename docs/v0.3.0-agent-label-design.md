# v0.3.0 design — pipeline-level literal agent labels

> **Status: planning only — not implemented.** This document proposes exactly
> one feature for v0.3.0. It does not change the parser, generator, reports,
> tests, version, tag, release, or any published asset. Baseline: `main` at
> `9f12240e6c9ef7ace5498aedb8dafb0bf5623993` (2026-11-19); current tool
> version `0.2.1`.

## 1. Problem and evidence

Today `agent any` is supported with an explicit `ubuntu-latest` assumption,
but every brace-form agent is a `PB-AGENT` blocker:

```groovy
agent { label 'nodejs' }          // PB-AGENT, pipeline disabled
agent { label "linux&&docker" }   // PB-AGENT, pipeline disabled
agent { node { label 'linux' } }  // PB-AGENT, pipeline disabled
agent none                        // PB-AGENT, pipeline disabled
```

That is correct for Docker, Kubernetes, and per-stage agents, which need a
job-graph or infrastructure translation that pipebridge does not have. It is
overly broad for the simplest and most common form: a pipeline-level literal
label that only selects an executor.

The compatibility study counts a custom or labeled agent in **7 of 7**
sample files (`docs/compatibility-study.md` §3). The checked-in synthetic
equivalents show why that headline count is not the same as "7 of 7 are
safely translatable":

| Synthetic equivalent | Agent form | Line | Other blocking evidence | Could a label-only feature make it clean? |
| --- | --- | --- | --- | --- |
| `node-minimal-do400-like` | `agent { label "nodejs" }` | 7–8 | none: three literal `sh` stages | **Yes** |
| `container-k8s-memphis-like` | `agent { label 'big-fleet' }` | 14–15 | prelude declaration, dynamic env, `script`, `withCredentials`, `post`, postlude | No |
| `infra-deploy-hmrc-like` | `agent { label 'docker' }` | 16 | prelude declarations, dynamic env, `script`, stage `dockerfile` agents, named `sh`, `stash`, `when`, `post` | No |
| `node-release-tutanota-like` | `agent { label 'main' }` | 24–25 | prelude, dynamic env, `parameters`, stage `script`, `when`, `post`, postlude | No |
| `python-app-couchbase-cli-like` | `agent { label "linux&&docker" }` | 14 | label is an expression, not a literal; imports, dynamic env, `post` | No |
| `java-maven-jetty-like` | `agent none` + stage `node` agents | 7, 18, 31 | options, `parallel`, `when`, `script`, shared-library calls, `post` | No |
| `python-gpu-kymatio-like` | `agent none` + stage `dockerfile` | 9, 17 | options, stage container, dynamic env, `post` | No |

Four of seven samples use a pipeline-level **simple literal** label
(DO400, Memphis, HMRC, Tutanota). One uses a label expression (Couchbase),
and two use `agent none` with per-stage agents (Jetty, Kymatio). Only DO400
is otherwise clean, so a label-only feature would take exactly **one** sample
from exit 2 to exit 0. It would still remove a foundational blocker from the
other three simple-label pipelines, even though their drafts remain disabled
for other reasons.

### Candidate frequencies

| Construct | Study count | Checked-in synthetic observation | Fully translatable by a narrow subset? |
| --- | --- | --- | --- |
| Custom/labeled agent | 7/7 | 4/7 pipeline-level simple labels, 1/7 expression label, 2/7 `agent none` | Yes for 4/7; 1/7 clean |
| `post` section | 4/7 | 6/7 synthetics contain `post` | Only 1/7 (`couchbase`) has literal `sh`/`echo` only |
| `options` directive | 2/7 | Jetty (four options, no timeout), Kymatio (three options, one timeout) | 1/7 exact `timeout`; 0/7 clean |
| `parallel` | 1/7 | Jetty only | No: loses shared workspace/job graph |
| `when` | 2/7 (Jetty, HMRC) | Jetty, HMRC; the synthetic Tutanota also has one | No: expressions/custom functions |

The synthetic set is a sanitized reconstruction, so its `post` count can
differ from the study's manual count. The table shows both where they differ;
the candidate comparison below uses the conservative translatable subset, not
the headline construct count.

## 2. Candidate comparison

Three bounded candidates were compared. The criteria are deliberately
independent: sample evidence, user value, implementation complexity, and
semantic risk. "Full sample unlock" means a checked-in sample can reach
exit 0 without any other feature.

| | C1: pipeline-level literal `agent { label '…' }` | C2: pipeline-level `post { always/success/failure }` with literal `sh`/`echo` | C3: pipeline-level `options { timeout(…) }` |
| --- | --- | --- | --- |
| **Sample evidence** | High: 4/7 simple labels; 7/7 have an agent blocker | Medium: 4/7 contain `post`, but only 1/7 has a translatable body | Low: 2/7 have options; 1/7 has an exact pipeline-level options timeout |
| **User value** | High: runner selection is required before any labeled pipeline can run; removes a blocker from 4/7 | Medium: notifications/cleanup are common, but most sample bodies use `junit`, `mail`, or shared-library calls | Medium-low: useful safety control, but only one exact sample and no clean pipeline |
| **Implementation complexity** | Low: parse one block, store one string, emit one `runs-on` list | Medium: new post model, condition parsing, conditional steps, report surface, ordering/status rules | Low: parse one option, store minutes, emit `timeout-minutes` |
| **Semantic risk** | Medium-high: Jenkins labels are not GitHub runner labels; a runner must exist and match the environment | Medium: Jenkins post conditions are evaluated after the pipeline; GitHub step conditions are evaluated in sequence, and a failing post step can change later conditions | Low-medium: Jenkins pipeline timeout and GitHub job timeout start/cancel differently |
| **Sample fully unlocked** | **DO400** | None (Couchbase still has an expression label) | None |
| **Verdict** | **Recommend** | Defer | Defer |

### Why C1

C1 is the only candidate that changes a real sample end to end. It also
attacks the first decision every migrated pipeline makes: where it runs. The
mapping is deliberately narrow — one literal label, pipeline level only — and
it is visible in the generated workflow (`runs-on: [self-hosted, label]`)
rather than hidden behind a new translation. The assumption is recorded as a
finding, so a human can review or replace it.

The risk is real: a Jenkins label does not guarantee that a GitHub self-hosted
runner with the same label exists, or that it has the same OS, tools, network,
and permissions. C1 therefore does not claim runner equivalence. It carries
the user's explicit label into a self-hosted runner selector and reports the
assumption. That is a bounded infrastructure mapping, not a claim that the
same machine or environment is selected.

### Why not C2

`post` is the more attractive-looking feature because the study counts it in
4/7 samples, but the sample evidence does not survive the narrow subset. The
checked-in synthetics add HMRC and Tutanota; in every case except Couchbase
the body is untranslatable. Jetty's `always` uses `junit` and a
shared-library call; Kymatio's `failure` uses `mail`; Tutanota's `failure`
uses `mail`; Memphis's success/failure bodies call shared-library helpers;
HMRC's `echo` interpolates `currentBuild.currentResult`. Only Couchbase has
literal `sh`/`echo`, and Couchbase is also blocked by its label expression. A
v0.3.0 post feature would therefore add a new model, condition semantics, and
report surface without unlocking a single sample. The condition ordering and
result-mutation differences are also a larger semantic surface than C1. This
is a good candidate **after** the runner question is settled, not before it.

### Why not C3

An exact `timeout` mapping is the smallest change and the lowest semantic
risk. It is also the least valuable in this sample: the study counts
`timeout` in 2/7 files, but only Kymatio puts it in the pipeline-level
`options` block (Jetty and Tutanota use stage-level `timeout` step wrappers,
which C3 would not touch). Kymatio's other options (`disableConcurrentBuilds`,
`buildDiscarder`) would remain blockers, and Jetty's options block has no
timeout at all. C3 would not unlock a sample and would not remove a
foundational blocker from the others. It is a reasonable follow-up increment,
not the v0.3.0 centerpiece.

### Candidates not shortlisted

`parallel` (1/7) changes the job graph and loses the shared workspace;
`when` (2/7) depends on expressions and custom functions; `stash`/`unstash`
introduces an artifact store and latency; `withCredentials` requires manual
secret configuration; `input` changes the deployment approval model; and
`docker`/`dockerfile`/`kubernetes` agents require a two-phase image or
infrastructure translation. None is as bounded as C1, and none is recommended
for v0.3.0.

## 3. Recommended feature: C1

**Translate one pipeline-level literal agent label to a self-hosted GitHub
Actions runner selector.** Nothing else about agent handling changes.

### 3.1 Exact accepted Jenkins syntax

The accepted form is exactly one pipeline-level agent block containing
exactly one `label` statement:

```groovy
pipeline {
    agent { label 'nodejs' }
    stages {
        // ...
    }
}
```

Both single- and double-quoted string literals are accepted:

```groovy
agent { label 'nodejs' }
agent { label "nodejs" }
```

A label is accepted only when all of the following are true:

- The `agent` block is at **pipeline level**, not inside a stage.
- The block contains exactly one statement: `label '<value>'` or
  `label "<value>"`.
- The value is a literal string. Groovy interpolation (`${...}` or `$name`),
  concatenation, method calls, and variables are rejected.
- The decoded value matches `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`.
  This permits letters, digits, `_`, `.`, and `-`; it excludes whitespace,
  `&`, `|`, `!`, `$`, `{}`, `()`, `*`, `?`, `/`, `\`, and `:`.
- `decoded_label.lower() != "self-hosted"`: the reserved GitHub label
  `self-hosted` is rejected in **any casing** (`self-hosted`, `SELF-HOSTED`,
  `Self-Hosted`, `sElF-hOsTeD`). This is the only case-insensitive
  comparison in the feature.
- Every other accepted label is carried through **unchanged, including
  case**: `agent { label 'NodeJS' }` produces
  `runs-on: [self-hosted, NodeJS]`, never `nodejs`.
- Escapes are decoded by the existing string decoder first, and the
  **decoded** value must match the label grammar. No escape sequence can
  produce an accepted label, because every escape the decoder understands
  yields the quoting character, a backslash, a dollar sign, or a control
  character — all outside the grammar. `label 'a\'b'` and `label 'a\\b'`
  are therefore rejected.
- There is no `node`, `docker`, `dockerfile`, `kubernetes`, `customWorkspace`,
  `retries`, `nodeProperties`, or any other directive in the block.
- There is no second pipeline-level `agent` section.

`agent any` remains supported exactly as today. A stage-level `agent any`
remains the existing no-op; this feature does not add any stage-level runner
mapping. `agent none` remains a blocker.

### 3.2 Generated GitHub Actions mapping

| Jenkins source | Generated workflow |
| --- | --- |
| `agent { label 'nodejs' }` | `runs-on: [self-hosted, nodejs]` |
| `agent { label "big-fleet" }` | `runs-on: [self-hosted, big-fleet]` |
| `agent { label 'node.js' }` | `runs-on: [self-hosted, node.js]` |
| `agent { label 'NodeJS' }` | `runs-on: [self-hosted, NodeJS]` (spelling preserved) |
| `agent any` | `runs-on: ubuntu-latest` (unchanged) |
| `agent { label 'x' }` with other blockers | `runs-on: [self-hosted, x]` in the disabled draft |

The job remains a single job. No `container:`, `services:`, `strategy`, or
new job is introduced. The existing `workflow_dispatch` trigger, permissions,
`defaults.run.shell`, implicit checkout, step generation, expression escaping,
and action pinning are unchanged.

Labels that look like YAML scalars are still emitted as **strings**. The
existing scalar-quoting rules quote them:

| Source label | Generated `runs-on` |
| --- | --- |
| `agent { label 'true' }` | `runs-on: [self-hosted, "true"]` |
| `agent { label 'null' }` | `runs-on: [self-hosted, "null"]` |
| `agent { label '123' }` | `runs-on: [self-hosted, "123"]` |
| `agent { label '1.2' }` | `runs-on: [self-hosted, "1.2"]` |

Parsing the generated YAML must return the list `["self-hosted", "true"]`
(and `["self-hosted", "null"]`, `["self-hosted", "123"]`,
`["self-hosted", "1.2"]`) with **every element a string**. A label is never
emitted or parsed as a boolean, null, or number, and its original spelling is
preserved.

The `runs-on` list is emitted whenever the label is accepted, even when a
different blocker disables the job. The draft therefore shows the intended
runner rather than silently falling back to `ubuntu-latest`. If the label is
rejected, the existing `runs-on: ubuntu-latest` skeleton is preserved and
`PB-AGENT` remains.

### 3.3 New assumption finding

Add one stable info code:

| Code | Severity | Meaning |
| --- | --- | --- |
| `PB-ASSUME-RUNNER-LABEL` | info | A Jenkins agent label was mapped to a self-hosted GitHub Actions runner label |

The finding is attached to the pipeline-level agent declaration and says, in
substance:

> Jenkins agent label `'nodejs'` was mapped to
> `runs-on: [self-hosted, nodejs]`. This assumes a self-hosted GitHub Actions
> runner with label `nodejs` exists and provides the same OS, installed
> tools, network access, permissions, and workspace behavior as the Jenkins
> agent. Jenkins label expressions, variables, and stage-level agents are not
> mapped.

`PB-ASSUME-RUNNER` remains the `agent any` → `ubuntu-latest` assumption and
is not emitted for a label mapping. Like the existing assumptions, the new
finding is emitted even when another blocker keeps the job disabled, so the
migration checklist still records the runner decision.

## 4. Unsupported variants that must remain blockers

Every variant below keeps the current disabled-draft behavior: the exit code
and the disabled draft are unchanged, and no new translation is enabled. The
finding set can change only by the code(s) listed in the Finding column; for
example an interpolated label adds `PB-INTERP` at the interpolation while
keeping `PB-AGENT`. If the variant is inside a stage, only that stage is
blocked; the rest of the pipeline may still translate, but the job stays
disabled because a blocker exists.

| Variant | Finding | Why it remains blocked |
| --- | --- | --- |
| `agent none` | `PB-AGENT` | Requires per-stage agents, which need a job graph |
| Stage-level `agent { label 'x' }` | `PB-AGENT` | All stages share one job; a per-stage runner would split the job and lose workspace state |
| `agent { label 'a&&b' }` or any label expression | `PB-AGENT` | Not a single literal label; GitHub runner labels are not a Jenkins label-expression evaluator |
| `agent { label "${AGENT}" }` / `$AGENT` | `PB-INTERP` plus `PB-AGENT` | Dynamic value; never evaluated |
| `agent { label '' }` | `PB-AGENT` | Empty label is not a runner selector |
| `agent { label 'self-hosted' }` / `'SELF-HOSTED'` / mixed case | `PB-AGENT` | Reserved GitHub label, compared case-insensitively; mapping would duplicate or hide the specific selector |
| Label longer than 64 characters | `PB-AGENT` | Outside the bounded grammar |
| Label with whitespace/operators/punctuation outside `[A-Za-z0-9_.-]` | `PB-AGENT` | Outside the bounded grammar |
| `agent { node { label 'x' } }` | `PB-AGENT` | `node` block semantics and additional directives are not modeled |
| `agent { docker … }`, `dockerfile { … }`, `kubernetes { … }` | `PB-AGENT` | Container/agent provisioning is a separate feature |
| `agent { label 'x' }` with extra directives, `agent { label('x') }` call form, or any other block shape | `PB-AGENT` | The block is not the accepted single-statement, string-literal form |
| Duplicate pipeline-level `agent` sections | `PB-SYNTAX` | Ambiguous runner selection |
| Unknown `agent` syntax | `PB-SYNTAX` | Not in the documented grammar |
| A stage-level `agent any` | none | Existing no-op, unchanged |

Additional invariants:

- A supported label does **not** make a malformed pipeline valid. Missing
  `stages`, an empty `steps`, or a missing stage remains exit 1.
- A supported label does **not** clear unrelated blockers. For example,
  Memphis and Tutanota still have prelude/parameter/script blockers, and
  HMRC still has stage-level `dockerfile` agents.
- A rejected label does **not** silently fall back to `ubuntu-latest` in a
  way that makes the pipeline look translated. It leaves `PB-AGENT` and the
  disabled draft in place.

## 5. Effects on reports, assumptions, and existing output

### Reports

- `PB-AGENT` is no longer emitted for an accepted pipeline-level literal
  label. It remains for every unsupported variant above.
- `PB-ASSUME-RUNNER-LABEL` (info) is added to the findings and to the
  report's `assumptions` code list.
- `PB-ASSUME-RUNNER` remains `agent any` only.
- The report JSON shape does not change: no new top-level key is required.
  The mapped runner is visible in `workflow.yml`; the report explains the
  assumption. `summary.blockers` and `summary.info` change only as described
  below.
- The Markdown report gains no new section; the new finding appears in the
  existing Assumptions section.
- `translated` changes only for pipelines that become eligible: DO400's
  stages move from "blocked, no steps" to translated `sh` steps.

## 8. Validation plan

### Unit and parser tests

- Accepted labels: single quote, double quote, hyphen, dot, underscore,
  digits, maximum length.
- Rejected labels: empty, reserved, too long, whitespace, `&&`, `||`, `!`,
  `$`, `${}`, `()`, `*`, `?`, `/`, `\`, `:`, escaped quote, escaped
  backslash, and escaped control characters (the decoded value is validated,
  not the raw text).
- Agent shapes: `agent any` (unchanged), `agent none`, stage-level label,
  `node`, `docker`, `dockerfile`, `kubernetes`, extra directives, duplicate
  pipeline agents.
- Assertions on `pipeline.blocked`, `pipeline.agent_label`, and finding
  code/severity/line/column.
- Interpolated labels emit `PB-INTERP` at the interpolation and `PB-AGENT`
  for the unsupported agent.

### Workflow tests

- `runs-on: [self-hosted, nodejs]` for an accepted label.
- `runs-on: ubuntu-latest` for `agent any`.
- YAML `safe_load` succeeds for every accepted label, including labels that
  need quoting.
- YAML round-trip: for each of `true`, `null`, `123`, and `1.2`, parse the

## 9. Limits on runtime-equivalence claims

This feature maps a **selector**, not an environment. It does not claim:

- that a self-hosted runner with the Jenkins label exists, is online, or is
  available;
- that the GitHub runner has the same OS, architecture, installed tools,
  network access, credentials, permissions, or workspace lifecycle as the
  Jenkins agent;
- that `runs-on: [self-hosted, label]` selects the same machine, image, or
  executor class as Jenkins;
- that GitHub runner-label matching (its default labels and its matching
  rules, including case handling) behaves like Jenkins label matching;
- that Jenkins label expressions, label variables, multiple labels, or
  stage-level agents are translated;
- that a successful conversion will run successfully, produce the same
  artifacts, or preserve Jenkins runtime behavior;
- that Docker, GPU, Kubernetes, or container-agent behavior is reproduced;
- that a Jenkins label which happens to look like a GitHub-hosted label
  (`ubuntu-latest`, for example) is treated as hosted. It is always treated
  as a self-hosted label; the user must edit `runs-on` deliberately if they
  want a hosted runner.

The only claim is: a literal pipeline-level label is carried into a
self-hosted GitHub Actions runner selector under the documented grammar, and
the assumption is reported. This is consistent with pipebridge's existing
`agent any` assumption, but it is an infrastructure assumption, not a
runtime-equivalence guarantee.

## 10. Implementation outline and out of scope

At implementation time (separate PR, not this one):

- `src/pipebridge/model.py`: add `agent_label` and its source span to
  `Pipeline`.
- `src/pipebridge/parser.py`: extend `_parse_agent` to recognize the exact
  pipeline-level `agent { label '<literal>' }` block; reject every other
  brace form; keep stage-level behavior unchanged. Accept the decoded value
  only when it matches the label grammar and
  `decoded_label.lower() != "self-hosted"`, then store the decoded value
  unchanged.
- `src/pipebridge/findings.py`: register `PB-ASSUME-RUNNER-LABEL` (info) and
  update the `PB-AGENT` description to "unsupported agent declaration".
- `src/pipebridge/analysis.py`: emit the new assumption once per accepted
  label; keep `PB-ASSUME-RUNNER` for `agent any`.
- `src/pipebridge/workflow.py`: emit the `runs-on` list when a label is
  present, otherwise the existing `ubuntu-latest`.
- Tests and goldens as described above; README and release documentation at
  release time.
- Version bump, changelog, release notes, tag, release, and assets belong to
  a later release PR and are out of scope here.

Explicitly out of scope for v0.3.0 C1:

- stage-level agent labels or any per-stage runner mapping;
- `agent none`, `node`, `docker`, `dockerfile`, `kubernetes`;
- label expressions, variables, concatenation, or a user-supplied label
  mapping table;
- runner provisioning or self-hosted runner setup;
- `post`, `options`, `parallel`, `when`, `stash`/`unstash`, credentials,
  `input`, or any other translation feature;
- runtime execution or Jenkins-equivalence testing;
- any change to v0.1.0, v0.2.0, or v0.2.1 tags, releases, or assets.
