# Design — literal `string` credential bindings → GitHub Actions secret references

> **Status: planning only.** This document describes a bounded first increment.
> It does **not** implement it, change code or tests, bump the version, create
> secrets or repositories, or alter any published release asset. The current
> parser still treats every `withCredentials` binding as a `PB-CRED` blocker
> and keeps its body opaque.

## 1. Problem and current evidence

Jenkins credentials are referenced by **credential ID**; GitHub Actions
secrets are referenced by **secret name**. The two namespaces are unrelated.
A conversion that guesses a mapping would either break at runtime or, worse,
inject the wrong secret into a step. The first increment therefore translates
one narrow binding form and requires an explicit, validated mapping.

### Current behavior

| Area | Current behavior |
| --- | --- |
| `withCredentials` in `steps` | `PB-CRED` blocker; the whole stage is not translated; the body is **not traversed** (`src/pipebridge/parser.py`, `_parse_steps`; `_diagnose_step` still reports it as an opaque boundary). |
| `credentials()` in `environment` | `PB-CRED` blocker (`_parse_env_value`); unchanged by this design. |
| Diagnostic traversal (D2) | `withCredentials` is deliberately **not** in `_WRAPPER_STEPS`; its body is a boundary, not analyzed content. This design does not widen D2. |
| Report | No credential plan, no required-secret list, and no setup checklist. |
| Workflow | A blocked stage becomes a `[NOT MIGRATED]` placeholder; the job is disabled with `if: false`. |

### Compatibility evidence

`docs/compatibility-study.md` §3 records `withCredentials` in **1 of 7**
sample files, and §5 says the GitHub `secrets` mapping is manual and
repository-config dependent. The two checked-in credential fixtures do not
use the narrow form this design proposes:

| Fixture | Credential form | Current blockers | Does this increment unlock it? |
| --- | --- | --- | --- |
| `tests/fixtures/container-credentials/Jenkinsfile` | `environment { NPM_TOKEN = credentials(...) }` and `usernamePassword(...)` | `PB-AGENT`, two `PB-CRED` | **No.** Both forms stay blocked. |
| `docs/compatibility-study/synthetic/container-k8s-memphis-like.Jenkinsfile` | `usernamePassword(credentialsId: 'docker-hub', …)` | prelude, dynamic env, `script`, `PB-CRED`, `post`, postlude | **No.** `usernamePassword` stays blocked. |
| `tests/test_reporting.py::test_markdown_report_blocker_details` | malformed `string(... usernameVariable: ...)` | `PB-CRED` | **No.** Unknown named arguments stay blocked. |

This increment is therefore a **safety and mapping foundation**, not a sample
unlock. New fixtures will cover the accepted form. The older fixtures become
regression evidence that unsupported credential forms and pre-existing
blockers are unchanged.

### Why this bounded form first

| Candidate | Evidence | Risk / reason to defer |
| --- | --- | --- |
| **C1: one literal `string(...)` binding** | Smallest credential form; one secret value → one environment variable; no file materialization or multi-variable semantics. | **Recommend.** |
| C2: `usernamePassword(...)` | Used by the checked-in samples. | Two variables, two secrets, and different GitHub naming decisions; expands the mapping surface and would invite guessing. Defer. |
| C3: `file(...)` / `sshUserPrivateKey(...)` | Common in deployment pipelines. | Requires materializing a temporary file with permissions, cleanup, and path semantics; no file-content handling is designed here. Defer. |
| C4: dynamic credential IDs | No deterministic static mapping. | Cannot be resolved without evaluating Groovy or asking Jenkins. Block. |

C1 is the right first step because it proves the **mapping, scope, gating, and
checklist** contract with the smallest possible grammar. The hard cases stay
blocked rather than approximated.

## 2. Accepted grammar

Only this form is accepted in the first increment:

```groovy
withCredentials([string(credentialsId: 'literal-id', variable: 'NAME')]) {
    sh 'command that reads "$NAME"'
    echo 'literal message'
}
```

### Grammar

```text
credential-statement :=
    "withCredentials" "(" "[" string-binding "]" ")" "{" body "}"

string-binding :=
    "string" "(" named-arg "," named-arg ")"

named-arg :=
    "credentialsId" ":" string-literal
  | "variable"      ":" string-literal

body := newline* step+ newline*
step := sh-step | echo-step | checkout-scm-step
```

Rules:

1. **Exactly one** `string(...)` entry in the list. The list contains no other
   binding, no second `string`, no trailing comma, and no nested list.
2. `credentialsId` and `variable` appear **exactly once each**, in either
   order. No other named arguments, no positional arguments, no `$class`.
3. Each value is a single- or double-quoted Groovy string token
   (`STRING_SQ` / `STRING_DQ`) decoded with the existing `decode_string`.
   Triple-quoted strings are not accepted for binding arguments.
4. The decoded `credentialsId` must be non-empty, must not have leading or
   trailing whitespace, and must not contain control characters. Internal
   spaces are allowed because Jenkins credential IDs are user-defined. The ID
   is matched **exactly** and **case-sensitively**.
5. The decoded `variable` must be a valid POSIX environment name:
   `^[A-Za-z_][A-Za-z0-9_]{0,127}$`. It must not start with the reserved
   GitHub prefixes `GITHUB_` or `RUNNER_` (case-insensitive check).
6. The body is one or more supported step statements using the existing
   `sh`, `echo`, and `checkout scm` argument grammars. Newlines, comments,
   semicolons, and ordinary whitespace between tokens are handled by the
   existing lexer/parser.
7. The body is a **steps list**, not a Groovy closure with arbitrary
   statements. No `script`, no `withCredentials`, no wrapper step (`timeout`,
   `retry`, `catchError`, `dir`, `withEnv`), no directive, and no unknown
   step.
8. A body step with an unsupported argument form is an unsupported body, not a
   partially translated binding.

### Translation semantics

- `NAME` is preserved as the **step environment variable** for every step in
  the binding body. It is not renamed to the secret name.
- The value is the GitHub expression `${{ secrets.MAPPED_NAME }}`, where
  `MAPPED_NAME` comes only from the explicit mapping.
- The mapping is by **credential ID**, so the same Jenkins ID used in several
  places resolves to the same secret name.
- `NAME` is available to the shell exactly as Jenkins would expose it. Shell
  text such as `sh 'echo "$NAME"'` is preserved; the secret is injected by the
  workflow runner, never substituted into the script text.
- Groovy interpolation is still blocked. `echo "token is $NAME"` remains
  `PB-INTERP`; the binding does not make interpolated Groovy strings
  supported.

Example generated step:

```yaml
      - name: Publish
        env:
          NPM_TOKEN: "${{ secrets.NPM_TOKEN }}"
        run: |2-
          npm publish
```

The YAML may quote the expression; after `yaml.safe_load` the value is exactly
`${{ secrets.NPM_TOKEN }}`. The expression is generated, not source-derived,
so it is **never** passed through `escape_github_expressions`.

## 3. Unsupported variants — all remain blocked

Every variant below stays a blocker in this increment. The enclosing stage is
not translated, and an unsupported binding body remains opaque (no mining for
`sh`/`echo`).

| Variant | Finding | Behavior |
| --- | --- | --- |
| `file(...)` | `PB-CRED` | Blocked. No file materialization, path, or cleanup translation. |
| `sshUserPrivateKey(...)` | `PB-CRED` | Blocked. No key-file or passphrase handling. |
| `usernamePassword(...)` | `PB-CRED` | Blocked. Two variables are not inferred from one string binding. |
| `usernameColonPassword(...)`, `certificate(...)`, `dockerCert(...)`, `gitUsernamePassword(...)`, any other binding type | `PB-CRED` | Blocked. |
| Two or more list entries, including two `string` entries | `PB-CRED` | Blocked at the list; body not traversed. |
| Nested `withCredentials` | `PB-CRED` | Blocked. Overlapping binding scope is not modeled. |
| `string(...)` with extra, missing, duplicate, or positional arguments | `PB-CRED` | Blocked. |
| Dynamic `credentialsId` or `variable` (identifier, method call, string interpolation) | `PB-CRED` | Blocked. The expression is not evaluated and no mapping is guessed. |
| Triple-quoted binding arguments | `PB-CRED` | Blocked. Only single/double-quoted literals are accepted. |
| Empty body, unterminated body, or body with an unsupported step/directive/wrapper | `PB-CRED` | Blocked; the body is not partially translated. |
| `credentials()` in `environment` | `PB-CRED` | Unchanged; not translated. |
| `withCredentials` outside `steps` | `PB-SYNTAX` / existing section blocker | Unchanged. |

A supported literal binding whose body is unsupported produces one
`PB-CRED` finding at the `withCredentials` token (with the reason, such as
“body contains unsupported step `timeout`”), not a partially translated
binding. This keeps the existing rule: a blocker clears the stage's steps.

## 4. Explicit credential-ID → secret-name mapping

### CLI surface

```sh
pipebridge convert Jenkinsfile \
  --output ./migration \
  --credential-map ./credential-map.json \
  --secrets-ready
```

- `--credential-map PATH` is optional. It is accepted by `analyze` and
  `convert`.
- `--secrets-ready` is an explicit acknowledgement that the required secrets
  have been created. It is accepted by `analyze` and `convert`; it never
  supplies or verifies a value.
- Neither flag adds a network call, invokes `gh`, or modifies GitHub.

### Mapping file format

JSON only, versioned, strict:

```json
{
  "schema_version": 1,
  "credentials": {
    "npm-registry-token": {
      "secret": "NPM_REGISTRY_TOKEN"
    },
    "docker-hub": {
      "secret": "DOCKER_HUB_TOKEN"
    }
  }
}
```

Rules:

1. The file is a JSON object with exactly two members: `schema_version` and
   `credentials`.
2. `schema_version` must be the integer `1` (not `"1"`, not `true`).
3. `credentials` is an object whose keys are Jenkins credential IDs and whose
   values are objects with exactly one member, `secret`, a string.
4. Duplicate JSON member names are rejected structurally (using
   `object_pairs_hook`); the last duplicate must never silently win.
5. No extra members anywhere. Unknown keys are errors, not ignored.
6. Credential IDs are matched exactly as written. The empty string, control
   characters, and leading/trailing whitespace are invalid keys.
7. Secret names follow the bounded rule
   `^[A-Z][A-Z0-9_]{0,99}$`, must not start with `GITHUB_` or `RUNNER_`, and
   are compared **case-insensitively** for collisions (GitHub secret names are
   case-insensitive). Requiring uppercase makes the rule deterministic and
   makes case-folding equivalent to exact comparison.
8. The mapping file itself is never copied into any generated artifact.
   Individual secret **names** appear only where they are required: the
   workflow's step `env:` expression, the report's credential section, and the
   setup checklist. Secret values are never part of the mapping file or any
   artifact.

### No silent guessing

The resolver MUST NOT:

- default a secret name to the variable name, the credential ID, or an
  uppercased/slugified form of either;
- trim, case-fold, normalize Unicode, or fuzzy-match credential IDs;
- resolve a missing ID from another ID, from the variable name, or from the
  environment;
- auto-suffix a secret name to break a collision;
- invent a secret name for an unresolved binding in the checklist;
- read a secret value from the environment, a file, `gh`, or the GitHub API.

If the exact ID is not in the map, the binding is unresolved.

### Validation and collision detection

| Check | Classification | Result |
| --- | --- | --- |
| Mapping path missing, unreadable, or a directory | Tool input error | Exit 1; no artifacts. |
| Invalid JSON | Tool input error | Exit 1; no artifacts. |
| Duplicate JSON member names | Structural error | Exit 1; no artifacts. |
| Wrong top-level shape, unknown keys, `schema_version != 1`, wrong value type, empty/control-character ID key | Structural error | Exit 1; no artifacts. |
| Source credential ID absent from the map | Resolution blocker | `PB-CRED-MAP`; exit 2; affected stage blocked; draft disabled. |
| Secret name violates the naming rule | Resolution blocker | `PB-CRED-MAP`; exit 2; affected stage blocked; no command emitted. |
| Two credential IDs map to the same secret name (case-insensitive) | Resolution blocker | `PB-CRED-MAP` at each affected binding; exit 2; affected stages blocked; no command emitted. |
| Binding variable collides with a pipeline/stage `environment` name in scope | Source blocker | `PB-CRED`; exit 2; stage blocked. No shadowing is guessed. |
| Mapping entry is valid but no source binding uses that ID | Info finding | `PB-CRED-MAP-UNUSED`; does not block. |
| Same credential ID used by several bindings | Allowed | All resolve to the same secret name; scopes remain independent. |

`--secrets-ready` cannot clear `PB-CRED`, `PB-CRED-MAP`, or any unrelated
blocker. It only changes the setup-acknowledgement blocker described next.

## 5. Draft gating and explicit readiness acknowledgement

### Findings

No existing code is renamed or renumbered.

| Code | Severity | Meaning |
| --- | --- | --- |
| `PB-CRED` | blocker (existing) | Unsupported credential construct or variant; unchanged broad meaning. |
| `PB-CRED-MAP` | blocker (new) | A supported binding has no valid explicit secret mapping (missing, invalid name, or collision). |
| `PB-CRED-SETUP` | blocker (new) | The mapping is resolved, but the user has not explicitly acknowledged that the required secrets exist. |
| `PB-CRED-MAP-UNUSED` | info (new) | A mapping entry is not referenced by this Jenkinsfile. |
| `PB-ASSUME-CREDENTIALS` | info (new) | The user acknowledged secret setup; pipebridge did not verify it. |

`PB-CRED-SETUP` is a blocker deliberately. It uses the existing disabled-draft
machinery (`if: false`) instead of inventing a second gating mechanism.

### State transitions

| State | Findings | Draft | Exit |
| --- | --- | --- | --- |
| No credential bindings | Existing behavior, plus empty `credentials` report section | Unchanged | Existing 0/2 |
| Supported binding, no map | `PB-CRED-MAP` | Disabled; stage placeholder | 2 |
| Supported binding, map missing ID | `PB-CRED-MAP` | Disabled; stage placeholder | 2 |
| Supported binding, invalid secret name or collision | `PB-CRED-MAP` | Disabled; stage placeholder; no command | 2 |
| Supported binding, map complete, no acknowledgement | `PB-CRED-SETUP` | Disabled; **steps generated with secret expressions for review** | 2 |
| Supported binding, map complete, `--secrets-ready` | `PB-ASSUME-CREDENTIALS` (info) | Enabled if there are no other blockers | 0 |
| Supported binding, map complete, `--secrets-ready`, unrelated blocker | `PB-ASSUME-CREDENTIALS` (info) + unrelated blocker | Disabled | 2 |
| Unsupported variant, even with `--secrets-ready` | `PB-CRED` | Disabled | 2 |
| Missing/unreadable/invalid mapping file | Tool input error | No artifacts | 1 |

When a mapping is unresolved, the affected stage is marked blocked during the
analysis pass and its steps are cleared, so no placeholder secret name and no
partial env mapping can be emitted. When only the setup acknowledgement is
missing, the steps **are** generated (so the reviewer can see the exact
`NAME: ${{ secrets.MAPPED_NAME }}` pairing) while the whole job remains
disabled. This makes the checklist and the draft reviewable together.

### Acknowledgement semantics

`--secrets-ready` means:

> The user asserts that every secret named in the generated checklist has been
> created in the target repository, with exactly that name. pipebridge did not
> verify it and never reads secret values.

It is recorded as `credentials.setup_acknowledged: true` and as the info
finding `PB-ASSUME-CREDENTIALS`. It is not a verification result. Passing the
flag with an incomplete map or an unsupported variant does not enable
anything.

## 6. Scope preservation and generated workflow rules

Invariants:

1. **Step scope only.** `NAME: ${{ secrets.MAPPED_NAME }}` is emitted in the
   `env:` map of each step inside the binding body. It is never added to
   `pipeline.env`, a stage's `environment`, or the job-level `env:` block.
2. **Binding ends at the closing brace.** Sibling steps before and after the
   binding have no credential env. The implicit checkout has no credential
   env.
3. **No shadowing.** If a pipeline/stage environment variable has the same
   name as the binding variable, the binding is blocked (`PB-CRED`); pipebridge
   does not guess which value Jenkins would win with.
4. **Independent scopes.** Two sequential `withCredentials` blocks may bind
   the same variable name; each applies only to its own steps. Overlap is
   possible only by nesting, and nesting is blocked.
5. **No secret text in scripts.** The secret name appears in the `env:` value
   and the setup checklist, never in a `run:` script. The binding variable
   remains the shell-visible name.
6. **Generated expressions are not escaped.** `escape_github_expressions` is
   applied only to source-derived text. The generated
   `${{ secrets.MAPPED_NAME }}` value is emitted through a separate path.
   Source text that happens to contain `${{ ... }}` continues to be
   neutralized (`PB-GHEXPR`), even inside a credential-bound step.
7. **Validated names prevent injection.** The secret name and variable name
   rules reject `${{`, quotes, newlines, colons, and YAML metacharacters.
   Report rendering still escapes Markdown table delimiters in credential IDs.
8. **No job-level convenience.** There is no option to hoist the binding to
   job scope. A user who needs the value across many stages must create
   separate bindings or change the pipeline deliberately.

## 7. Report and setup checklist

### JSON report addition

Add one top-level `credentials` object. All existing top-level keys, finding
keys, `translated` entry keys, and `summary` keys keep their current types and
meaning. This is an additive schema change; the existing schema-guard test is
updated deliberately.

```json
{
  "credentials": {
    "map_supplied": true,
    "setup_acknowledged": false,
    "bindings": [
      {
        "credential_id": "npm-registry-token",
        "variable": "NPM_TOKEN",
        "secret_name": "NPM_REGISTRY_TOKEN",
        "stage": "Publish",
        "source_line": 24,
        "status": "resolved",
        "reason": null
      }
    ],
    "required_secrets": ["NPM_REGISTRY_TOKEN"],
    "checklist": [
      {
        "secret_name": "NPM_REGISTRY_TOKEN",
        "credential_ids": ["npm-registry-token"],
        "variables": ["NPM_TOKEN"]
      }
    ]
  }
}
```

- `bindings` is in source order.
- `status` is one of `resolved`, `missing_mapping`, `invalid_secret_name`,
  `collision`, or `unsupported`.
- `required_secrets` contains only resolved names, sorted lexicographically.
- `checklist` is deduplicated by secret name and sorted the same way.
- An unresolved binding has `secret_name: null`, a non-null `reason`, and no
  checklist command. pipebridge does not invent a name.
- The object is present even when there are no credential bindings, as an
  empty, stable shape. This is why the schema guard changes; workflow bytes do
  not.

### Markdown section

When at least one credential binding is present, `migration-report.md` gains a
section like:

```markdown
## Required GitHub Actions secrets

pipebridge never reads, prints, embeds, or invents secret values. It only
knows the secret names supplied in the mapping file.

| Credential ID | Bound variable | GitHub secret | Status |
| --- | --- | --- | --- |
| `npm-registry-token` | `NPM_TOKEN` | `NPM_REGISTRY_TOKEN` | resolved |

### Create each secret

GitHub UI:

1. Open the target repository on GitHub.
2. Go to **Settings → Secrets and variables → Actions**.
3. Select **New repository secret**.
4. Enter the name **exactly** as shown above (for example
   `NPM_REGISTRY_TOKEN`).
5. Enter the value yourself. pipebridge never sees, prints, or stores it.
6. Select **Add secret**.

`gh` CLI, from a clone of the target repository with `gh auth login` already
completed:

```sh
gh secret set NPM_REGISTRY_TOKEN
# gh prompts for the value; do not pass the value on the command line.
```

Outside the clone, add `--repo <owner>/<repo>` yourself. pipebridge does not
guess or invent the repository.

After every secret above exists, re-run the same conversion with the same
`--credential-map` plus `--secrets-ready`. That flag is an acknowledgement,
not a verification: pipebridge still does not read or test the secret.
```

For unresolved or blocked bindings, the table shows the reason and the text
says an explicit mapping is required. No secret name or command is generated
for that row. There is no `--body` instruction and no value anywhere in the
report, JSON, workflow, or logs.

## 8. Model, parser, and reporting boundaries

### Model

Add a frozen `CredentialBinding` value to `model.py`:

```text
credential_id: str
variable: str
secret_name: str | None
status: resolved | missing_mapping | invalid_secret_name | collision | unsupported
reason: str | None
span: Span
```

`Step` gains `credentials: tuple[CredentialBinding, ...] = ()`. `Stage`,
`Pipeline`, and `EnvVar` gain no credential fields: scope lives on the step,
which is the only place it is allowed to be emitted.

### Parser

- Add `_parse_with_credentials(stage, span)` in `_parse_steps`, before the
  generic `withCredentials` blocker branch.
- Parse the exact grammar above with the existing lexer tokens and
  `decode_string`; do not evaluate anything.
- Parse the body into steps only if every body statement is a supported step
  with a supported argument form. On any failure, emit one `PB-CRED` at the
  binding, clear the stage, and leave the body opaque. Do not emit a partial
  binding.
- Keep `_diagnose_step` behavior for unsupported variants: report `PB-CRED`
  once and skip the body. Do not add `withCredentials` to `_WRAPPER_STEPS`.
- Reject a binding variable that collides with a pipeline/stage environment
  name in scope.

### Mapping/resolution

Add a small `src/pipebridge/credentials.py` module:

- strict JSON loading with duplicate-key detection;
- schema and naming validation;
- exact ID lookup and collision detection;
- production of resolved bindings, `required_secrets`, checklist data, and
  mapping findings.

`analyze_source` gains the resolved mapping/plan (or the CLI passes it into a
post-parse resolution step). On `PB-CRED-MAP`, mark only the affected stages
blocked and clear their steps. Do not touch stages without credential
bindings.

### Workflow generation

- In `_generate_steps`, emit step `env:` entries from
  `step.credentials` for resolved bindings, merged with stage env only after a
  collision check.
- Use `_yaml_scalar` for the generated expression value; use a separate
  generated-expression path so `escape_github_expressions` is not applied.
- Never write credential env to job or pipeline scope.
- The existing `if: false` path handles `PB-CRED-MAP` and `PB-CRED-SETUP`
  without a second mechanism.

### CLI

- Add `--credential-map` and `--secrets-ready` to both `analyze` and
  `convert`.
- Read the mapping once; structural/read errors are exit 1 with no artifacts.
- Resolution errors are findings and exit 2, so a disabled draft and the
  checklist are still produced.
- Keep the existing atomic staged-write/rollback behavior and output file set
  unchanged. The checklist is part of the existing reports, not a new output
  file.

## 9. Test criteria

### Grammar and translation

1. One literal `string` binding with `sh`, `echo`, and `checkout scm` in the
   body is accepted; every body step is named and translated in order.
2. Both quote forms, both named-argument orders, multiline formatting, and
   comments between tokens are accepted.
3. `NAME` is emitted as the step env key; the value is exactly
   `${{ secrets.MAPPED_NAME }}` after YAML parsing.
4. Source positions for the binding and its findings point at the exact
   `withCredentials` / argument tokens.
5. Groovy interpolation in `sh`/`echo` remains `PB-INTERP`; the binding does
   not make interpolated strings supported.

### Scope

6. Bound steps have the env entry; sibling steps before and after do not; the
   implicit checkout and job-level `env:` do not.
7. A multi-step binding applies the env to every body step.
8. Stage env is merged on bound steps; a same-name pipeline/stage env variable
   blocks with `PB-CRED` rather than silently shadowing.
9. Two sequential bindings keep independent scopes; a nested binding is
   blocked.
10. `pipeline.env` and `stage.env` never gain a credential variable.

### Escaping and injection

11. The generated workflow parses with `yaml.safe_load`; the secret expression
    survives exactly and is not neutralized by `escape_github_expressions`.
12. Source text containing `${{ ... }}` inside a bound `sh` is still escaped
    and reported as `PB-GHEXPR`; it does not become a real secret reference.
13. Invalid secret names (`${{`, quotes, newlines, lowercase, leading digit,
    `GITHUB_`/`RUNNER_` prefix, over-length) are rejected; no invalid name is
    emitted as an `env:` value or checklist command. It may appear only as
    escaped diagnostic text explaining the rejection.
14. Invalid variable names and reserved prefixes are rejected.
15. `run:` scripts never contain the secret expression; only `env:` does.

### Duplicate bindings and collisions

16. Two entries in one list, two nested bindings, and duplicate named
    arguments are blocked with `PB-CRED`.
17. The same ID/variable in two sequential bindings is allowed and each scope
    is independent.
18. The same variable from different IDs in non-overlapping scopes is allowed.
19. Two IDs mapping to the same secret name (including case-folded) produce
    `PB-CRED-MAP` for both; no checklist command is generated.
20. Duplicate JSON keys are rejected structurally (exit 1), not last-wins.
21. A stage/pipeline env name collision is blocked; no implicit precedence is
    invented.

### Malformed input and hard blockers

22. Missing comma/colon, wrong brackets, empty list, extra/positional args,
    triple quotes, non-literal IDs, and empty/unterminated bodies produce a
    blocker and exit 2, never a crash or a partial binding.
23. `file(...)`, `sshUserPrivateKey(...)`, `usernamePassword(...)`,
    `usernameColonPassword(...)`, and other binding types remain `PB-CRED`.
24. `credentials()` in `environment` remains `PB-CRED`.
25. Bodies containing `script`, `timeout`, unknown steps, or nested
    `withCredentials` remain blocked and are not traversed for translation.
26. Existing required-structure errors (no `stages`, no stage, empty `steps`)
    still exit 1.

### Gating and acknowledgement

27. No map + supported binding → `PB-CRED-MAP`, exit 2, stage placeholder,
    disabled job, no invented name.
28. Valid map missing the ID → same.
29. Invalid secret name / collision → same, no command.
30. Complete map, no `--secrets-ready` → `PB-CRED-SETUP`, exit 2, disabled job,
    but steps and env expressions are present for review.
31. Complete map + `--secrets-ready`, no other blockers → exit 0, enabled job,
    info `PB-ASSUME-CREDENTIALS`, no secret values.
32. `--secrets-ready` with an incomplete map or unsupported variant does not
    clear the blocker.
33. An unrelated blocker (`when`, `post`, etc.) still disables the job even
    with a complete map and acknowledgement.
34. `--secrets-ready` without any credential binding or mapping file is a
    no-op: workflow bytes unchanged, no credential finding.
35. Missing/unreadable/invalid JSON/schema mapping files exit 1 and write no
    artifacts.

### Setup checklist and no-secret-values invariant

36. The Markdown section lists every resolved secret name exactly once, with
    GitHub UI steps and a `gh secret set NAME` command.
37. The checklist never contains `--body`, a secret value, or a guessed name;
    unresolved rows say mapping is required.
38. The JSON `credentials` object has the documented shape, stable ordering,
    and no secret values.
39. A sentinel value placed in the process environment (for example
    `NPM_TOKEN=do-not-leak`) never appears in `workflow.yml`,
    `migration-report.md`, `migration-report.json`, or stderr.
40. No `gh` invocation or GitHub API call is made; a test fails if the code
    tries to execute `gh` or read a secret value.

### Unchanged existing behavior

41. `tests/fixtures/build-and-test` and the shipped
    `examples/python-build/migration/workflow.yml` are byte-identical.
42. `tests/goldens/pure-declarative/*.workflow.yml` are byte-identical.
43. `tests/fixtures/container-credentials` and the Memphis synthetic keep
    their current blocker codes and disabled workflow bytes; they are not
    partially converted.
44. `tests/test_reporting.py::test_markdown_report_blocker_details` keeps
    `PB-CRED` for the malformed `string` example.
45. All existing tests pass on Python 3.10 and 3.13; the only expected schema
    test update is the additive `credentials` top-level key.
46. CI runs actionlint 1.7.12 on generated workflows, the installed-CLI smoke
    test, and the python-build example validation successfully.

## 10. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Secret value leakage | Only names are accepted. No value read/print/embed path exists. Sentinel-value tests, no `gh`, no GitHub API. |
| Scope leak to job/stage env | Model stores bindings on `Step` only; tests assert no job/stage env additions. No hoisting option. |
| Silent guessing | Exact ID lookup; unresolved/collision findings; no default, trim, case-fold, slug, or fuzzy match. |
| Draft enabled without setup | `PB-CRED-SETUP` blocker plus `--secrets-ready`; unrelated blockers still dominate. |
| Escaping/injection | Strict name regexes; generated expression uses a separate path; YAML/actionlint tests; source `${{` still neutralized. |
| Duplicate/collision ambiguity | Duplicate JSON keys reject structurally; secret-name collisions block; env-name collisions block. |
| Malformed binding partially translated | Body is parsed only for the exact supported grammar; any failure clears the stage and leaves the body opaque. |
| Regression in existing output | Byte-level goldens for clean fixtures and examples; explicit keep-blocked tests for existing credential fixtures. |
| Report schema surprise | Additive `credentials` key; existing keys/types unchanged; schema guard updated deliberately; docs state the new key. |
| Scope creep into file/SSH/username-password/dynamic IDs | Hard-blocker table in §3; future milestones are recorded separately and not designed here. |

## 11. Bounded implementation sequence

Each step is a reviewable commit/PR; none merges, tags, releases, or creates
secrets by itself.

1. **Model and parser** — add `CredentialBinding`/`Step.credentials`; parse the
   exact accepted form; keep every other variant blocked; tests for grammar,
   scope, and unchanged existing workflows.
2. **Mapping and resolution** — strict JSON schema, exact lookup, naming,
   collision detection, `PB-CRED-MAP`/`PB-CRED-MAP-UNUSED`; stage blocking.
3. **Acknowledgement and workflow emission** — `PB-CRED-SETUP`,
   `--secrets-ready`, step env emission, escaping/scope tests.
4. **Report and checklist** — additive JSON `credentials` object, Markdown
   section, sentinel-value and no-`gh` tests, schema-guard update.
5. **Hardening** — fixture matrix for unsupported variants, malformed input,
   collisions, unrelated blockers, byte-level goldens, actionlint/example
   verification on 3.10 and 3.13.

Expected size: one parser path, one small mapping module, a model field, a
workflow emission branch, a report section, and tests. No new dependencies.

## 12. Acceptance criteria

1. The only accepted credential construct is the exact literal single
   `string` binding grammar in §2.
2. `NAME` is a step-scoped environment variable backed by
   `${{ secrets.MAPPED_NAME }}`; it never appears at job or stage scope.
3. Every accepted binding has an explicit, validated, exact credential-ID →
   secret-name mapping; missing, invalid, or colliding mappings block with no
   guessed name.
4. A complete mapping without explicit acknowledgement keeps the draft
   disabled; `--secrets-ready` is the only acknowledgement and does not verify
   or read values.
5. The report includes a setup checklist with required secret names, GitHub UI
   steps, and `gh secret set` instructions; it never retrieves, prints, embeds,
   or invents a value.
6. File, SSH, username/password, dynamic IDs, nested/multiple bindings, and
   unsupported bodies remain blocked in this increment.
7. Existing clean workflows and fixtures remain byte-identical; existing
   credential fixtures remain blocked with their current codes.
8. The full suite passes on Python 3.10 and 3.13, actionlint 1.7.12 is clean on
   generated workflows, and the example validation passes.
9. This design PR itself changes only documentation: no code, tests, version,
   tags, releases, secrets, or repositories.

## 13. Future milestones (recorded only, not implemented or expanded here)

These are separate milestones. This design does not implement them, define
their grammar, or expand their scope.

### F1 — Shell-helper extraction into `scripts/`

A later milestone may extract literal shell bodies into versioned helper
scripts under `scripts/` and reference them from generated workflows. This
design does not choose a file layout, parameterization, quoting model,
ordering, or parser behavior for that work. It remains a separate planning and
implementation effort.

### F2 — Shared-library migration guidance

A later milestone may add guidance for mapping `@Library` usage and
shared-library custom steps. This design does not resolve libraries, translate
custom steps, or widen analysis. `PB-LIB` remains a blocker, and the current
opaque-library boundary is unchanged.

## 14. Non-goals for this increment

- Reading, printing, embedding, inventing, or creating secret values.
- Creating repositories, secrets, environments, or GitHub configuration.
- Calling `gh`, the GitHub API, or Jenkins.
- Translating `file`, SSH, username/password, certificate, Docker, or other
  binding types.
- Evaluating Groovy, dynamic credential IDs, or interpolated strings.
- Hoisting credentials to job scope.
- Changing the `if: false` disabled-draft rule, report exit codes, or atomic
  write behavior.
- Version bump, tag, release, publication, or modification of existing
  releases.
- Implementing or expanding the F1/F2 future milestones.
